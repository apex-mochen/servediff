What each servediff fact key means

Each entry is one key, or one family when every key in it shares a meaning. The third paragraph is the one that matters: what the number does not answer, which is how a diff gets misread.

servediff explain kv_cache.max_concurrency
  • after_ready — Errors printed after the server reported ready -- during serving or shutdown.
  • api — Frontend behaviour: tool parser loaded, request fields the server accepted and then ignored, and chat-template ordering rules it rewrote.
  • arg — What the command line asked for
  • args — Which block the args were read from and how complete it is.
  • attn — The attention backend as the platform printed it when the usual `Using X attention backend` line never appears (CPU builds); the value is the enum's short name.
  • backend — Which kernel the build chose for each job -- attention, MoE, linear, all-reduce, sampling -- and, in backend.candidates, the set it would have considered.
  • cache — Request-level cache behaviour: prefix caching, radix tree, chunked prefill
  • chat — Chat template warmup: whether the template compiled at startup and how long it took.
  • compile — torch.compile / inductor on the backbone: backend, ranges compiled, fusions enabled, seconds spent, and why a recompile happened.
  • cpu — CPU-side threading and affinity: torch threads, OMP threads, NUMA mode and membind, reserved cores, and the core ids bound.
  • cuda_graph — CUDA graph capture: mode, how many graphs, seconds and GiB spent, and the pool they reserve; cuda_graph.profiling says whether the profile pass includes them.
  • engine — Which build served: version string, git sha when the log carries one, platform it ran on, engine.init_s for construction time
  • env — The environment the server ran in: the collect_env block vLLM asks every bug report to paste, plus SGLang's equivalent
  • gdn — Gated delta net kernels: which one is used for prefill and which for decode.
  • gpu — Per-device memory accounting, phase by phase: total and free before weights, the budget the utilization fraction allows, what was consumed after profiling, what CUDA graphs reserved, and the peak activation the profile run saw.
  • jit — JIT behaviour inside the startup window: warmup seconds, and the mode used for compiles that happen during inference.
  • kernel — Kernel-level choices and events: JIT during inference, FlashInfer autotune, and the final IR op priority per fused operator.
  • kv_cache — The cache the engine sized after profiling: GiB and tokens it holds, the sequence length and concurrency that implies, its dtype and block layout, and anything the engine had to pad or set aside.
  • mamba — State cache for hybrid/Mamba models: its size, and the effective size after the scheduler raised it to what the decode side needs.
  • mm — Multimodal behaviour: whether the model is effectively text-only, whether the per-frame pixel cap is applied, the encoder cache budget, chunked mm input, prefix attention, and the multimodal warmup seconds.
  • model — What was served: architecture, max length, supported tasks, and the dtype the weights were cast to
  • model_init — Time spent constructing the nn.Module before weights are read.
  • model_loading — The loader's own accounting of reading the checkpoint: GiB resident after load and the seconds it took.
  • model_runner — A marker, not a number: the log came from the V1 engine (gpu_model_runner).
  • moe — MoE configuration the engine settled on.
  • nccl — The collective library: version, and any environment overrides that changed how it behaves.
  • parallel — The parallel layout the process actually runs: TP, PP, DP, world size, the roles assigned to ranks, and whether TP exceeds the GPUs present.
  • pd — Prefill/decode disaggregation warmup, as a startup step.
  • plugins — Plugin registrations the server made: which name replaced which (`plugins.loaded: a -> b`).
  • quant — Quantization as the build reports it: checkpoint format, the kernel selected, and the per-layer choice when the log lists it.
  • ray — Ray's environment handling: which variable prefixes the workers inherit.
  • sampling — Sampling kernel and overrides: which top-k/top-p implementation ran, whether it fell back, and which request settings were overridden by spec decoding.
  • sched — Scheduler limits that were changed from what was configured: max scheduled tokens from spec settings, max running requests capped by a state cache.
  • scheduler — The scheduler's decisions: async scheduling on or off (and the reason), chunked prefill, and how it exited.
  • server — The HTTP surface: the URL it binds, the command line it was started with, the tasks it advertises, and whether scale-out is enabled.
  • serving — How the served endpoint formats content (chat template content format).
  • spec — Speculative decoding specifics: draft length, MTP layer reuse and whether the draft shares embedding/lm_head weights with the target.
  • startup — How startup ended: ready, or failed and at which stage
  • torch — The CUDA allocator's own OOM report: which device, how much was requested, how much was free at that instant, the card's total, and torch.oom_holder_gib -- the GiB another process was holding.
  • transfer — KV transfer between prefill and decode workers: staging buffers, their size and method, the custom memory pool, and the NIXL backend.
  • triton — Triton driver/library versions as the log prints them.
  • uva_buffers — Whether Unified Virtual Addressing buffers could use pinned memory, and what the server fell back to.
  • weights — Where the weights came from and how they were read: format, filesystem, cache, download and load seconds, checkpoint size, dtype, available RAM, and whether prefetch was possible (weights.prefetch says why not).

after_ready

Measured in: exception text

Errors printed after the server reported ready -- during serving or shutdown.

What it does not tell you: these say nothing about startup configuration, which is why they are kept apart from startup.error

api

Measured in: labels, a dict of ignored fields

Frontend behaviour: tool parser loaded, request fields the server accepted and then ignored, and chat-template ordering rules it rewrote.

What it does not tell you: api.ignored_request_fields is the frontend telling you your request was not fully honoured; a benchmark that ignores it measures something else

arg

Measured in: the flag's own unit

What the command line asked for. vLLM prints only non-default args, so an absent arg.X means 'default', not 'unset'; SGLang prints its whole server_args dict. args.source names the block the values came from.

What it does not tell you: asked is not used: enforce_eager, hybrid dtype rewrites and kv-cache sizing all override an arg, and the non-arg facts are where the used value lives

args

Measured in: a label

Which block the args were read from and how complete it is.

What it does not tell you: vLLM's block is a diff against defaults, SGLang's is the full set -- an arg comparison across engines is not symmetric

attn

Measured in: backend name

The attention backend as the platform printed it when the usual `Using X attention backend` line never appears (CPU builds); the value is the enum's short name.

What it does not tell you: here `default` means no flag won and the platform default did, which is not the same as an explicitly configured backend

backend

Measured in: backend names

Which kernel the build chose for each job -- attention, MoE, linear, all-reduce, sampling -- and, in backend.candidates, the set it would have considered.

What it does not tell you: a chosen backend that did not change can still sit on a list that shrank; that is why candidates is a fact of its own

backend.attention

Measured in: backend name

The attention backend the engine selected after its own checks, which is not always the one the flag asked for (backend.attention_forced says when it was overridden).

What it does not tell you: FlashInfer and FlashAttention are different kernel sets for the same command line, so this key is the one to read before comparing tokens/s

backend.moe

Measured in: backend name

The MoE backend chosen, with the quantization it runs in when the log names it (e.g. VLLM_CUTLASS (NvFp4)).

What it does not tell you: the same name over a different quantization is a different kernel -- read the parenthesised part

cache

Measured in: a label, or a size

Request-level cache behaviour: prefix caching, radix tree, chunked prefill. These change what the server does, not what it allocated.

What it does not tell you: a disabled prefix cache usually costs throughput, not correctness, so it can hide in a diff that only looks at latency

chat

Measured in: a label, milliseconds

Chat template warmup: whether the template compiled at startup and how long it took.

What it does not tell you: a template that warms up here can still fail on a request shape the warmup did not cover

compile

Measured in: seconds, token ranges

torch.compile / inductor on the backbone: backend, ranges compiled, fusions enabled, seconds spent, and why a recompile happened.

What it does not tell you: compile.total_s hides which phase grew; compile.dynamo_s, graph_s and warmup_s split it

cpu

Measured in: counts, ids

CPU-side threading and affinity: torch threads, OMP threads, NUMA mode and membind, reserved cores, and the core ids bound.

What it does not tell you: torch_parallelism on a many-core box can be far above the useful number and cost startup time; it is a real fact, not a typo

cuda_graph

Measured in: count, seconds, GiB

CUDA graph capture: mode, how many graphs, seconds and GiB spent, and the pool they reserve; cuda_graph.profiling says whether the profile pass includes them.

What it does not tell you: capture time is startup time and pool GiB is memory the cache cannot use; two runs can differ in both and only one of them is a regression

engine

Measured in: version, sha, seconds

Which build served: version string, git sha when the log carries one, platform it ran on, engine.init_s for construction time. Two logs whose facts are identical but whose versions differ are not the same run, because the reading rules change.

What it does not tell you: init_s is engine construction (weights, compile, cache sizing) and excludes a model download that happened before the process started

engine.init_s

Measured in: seconds

How long the engine took to construct, as the engine itself timed it.

What it does not tell you: it ends when init returns, so the first CUDA graph capture and any lazy warmup that happens on the first request are outside it

env

Measured in: versions, paths, environment variables

The environment the server ran in: the collect_env block vLLM asks every bug report to paste, plus SGLang's equivalent. `env.pip.*` says whether a wheel was importable and at which version; `env.var.*` is an environment variable the server printed; `env.ulimit.*` is the process limit.

What it does not tell you: a version here is a wheel that imported, not necessarily the kernel that ran, and two runs on the same versions can still differ in what they selected -- read env next to the other facts, never instead of them

gdn

Measured in: kernel names

Gated delta net kernels: which one is used for prefill and which for decode.

What it does not tell you: the two are chosen separately, so a prefill speedup can leave decode untouched

gpu

Measured in: GiB; utilization is a fraction of total

Per-device memory accounting, phase by phase: total and free before weights, the budget the utilization fraction allows, what was consumed after profiling, what CUDA graphs reserved, and the peak activation the profile run saw.

What it does not tell you: free_gib is measured before anything is loaded, and the OOM that follows is judged against consumed_gib -- the two are not the same pool

gpu.model

Measured in: a name

The card the log named.

What it does not tell you: vLLM prints it once per process in some versions; on a multi-GPU box it is the card the rank reporting happened to run on

gpu.utilization_effective

Measured in: fraction of total device memory

The utilization fraction the run actually reached (consumed / total), which vLLM prints as `equivalent to --gpu-memory-utilization=X`.

What it does not tell you: the value you passed and the value reached are different facts; a run that asked for 0.90 and reached 0.77 has 13% of the card idle, and that is the number to compare before blaming the model

gpu.utilization_to_match_kv_cache

Measured in: fraction of total device memory

What --gpu-memory-utilization you would have had to pass to get the KV cache you asked for.

What it does not tell you: it is advice printed after the engine failed to fit the cache, so it describes a configuration that was never run

jit

Measured in: seconds, mode name

JIT behaviour inside the startup window: warmup seconds, and the mode used for compiles that happen during inference.

What it does not tell you: a JIT that runs during inference stalls requests instead of startup; that is why kernel.jit_during_inference exists separately

kernel

Measured in: a label or an op name

Kernel-level choices and events: JIT during inference, FlashInfer autotune, and the final IR op priority per fused operator.

What it does not tell you: kernel.ir_op.* is the priority list after platform defaults, so a diff there is a change in which fused op wins, not in what you asked for

kv_cache

Measured in: GiB for sizes, tokens for tokens, sequences for concurrency

The cache the engine sized after profiling: GiB and tokens it holds, the sequence length and concurrency that implies, its dtype and block layout, and anything the engine had to pad or set aside.

What it does not tell you: this is what the engine decided the cache is, after auto-fitting; what you asked for is in arg.kv_cache_dtype / kv_cache.requested_gib

kv_cache.max_concurrency

Measured in: sequences

How many concurrent sequences the cache holds at the per-request token count the same sentence names.

What it does not tell you: it divides by that sentence's token count, not by your real request size -- at half the length you get roughly twice the concurrency

kv_cache.non_kv_gib

Measured in: GiB

The part of the memory split that is not the KV cache: weights plus the buffers the engine keeps outside it.

What it does not tell you: in the extensible-cache split this is a residual, so it grows when the cache shrinks without any weight changing

kv_cache.padding_waste

Measured in: percent of KV memory, as an upper bound

The upper bound the cache planner prints for KV memory that padding layers could waste, added so caches with different block sizes share one page layout (kv_cache.padding_layers says how many layers).

What it does not tell you: the log says 'may waste at most', so this is not the measured waste of an allocated cache: multiplying it into a memory estimate overstates the loss. A ratio measured from allocated pools and this printed ceiling are different quantities; comparing them reads as a contradiction that is not there

kv_cache.requested_gib

Measured in: GiB

The cache size you asked for, when the version supports sizing it directly (--kv-cache-memory) instead of through a utilization fraction.

What it does not tell you: asking is not getting: the engine prints what it actually allocated next to it, and the difference is what a later short-sequence OOM is about

kv_cache.suggested_gib

Measured in: GiB

The --kv-cache-memory the engine suggests when the utilization fraction cannot express what it needs.

What it does not tell you: the suggestion is derived from one profile pass; a suggestion quoted in an issue is that run's number, not a property of the model

kv_cache.tokens

Measured in: tokens

Total tokens the cache can hold, across all sequences.

What it does not tell you: tokens are the invariant here; the GiB moves with the dtype and the block layout

mamba

Measured in: slots, GiB

State cache for hybrid/Mamba models: its size, and the effective size after the scheduler raised it to what the decode side needs.

What it does not tell you: the effective size can differ per DP/TP/EP rank in one launch, and the cap it imposes on concurrency is a different key (sched.max_running_requests)

mm

Measured in: labels, tokens, seconds

Multimodal behaviour: whether the model is effectively text-only, whether the per-frame pixel cap is applied, the encoder cache budget, chunked mm input, prefix attention, and the multimodal warmup seconds.

What it does not tell you: mm.text_only means every modality limit was 0, so the vision tower never ran -- the absence of every other mm.* fact is the evidence, not a reading gap

model

Measured in: names, token counts, dtypes

What was served: architecture, max length, supported tasks, and the dtype the weights were cast to. model.cast is the pair `checkpoint dtype -> running dtype`.

What it does not tell you: architecture is what the config declared; the backend keys are what the build actually ran with for that architecture

model_init

Measured in: seconds

Time spent constructing the nn.Module before weights are read.

What it does not tell you: on a big model this is often small next to model_loading; a change here points at transformers or model code, not at the disk

model_loading

Measured in: GiB, seconds

The loader's own accounting of reading the checkpoint: GiB resident after load and the seconds it took.

What it does not tell you: the GiB here is what the weights occupy, not what the card used -- CUDA context, allocator and non-torch buffers are outside it

model_runner

Measured in: a label

A marker, not a number: the log came from the V1 engine (gpu_model_runner).

What it does not tell you: the V0 engine printed a different runner line, so a V0-vs-V1 comparison shows as this key appearing rather than changing

moe

Measured in: a label

MoE configuration the engine settled on.

What it does not tell you: an absent MoE config is not a bug on a dense model; it only matters when the architecture has experts

nccl

Measured in: version, NAME=value

The collective library: version, and any environment overrides that changed how it behaves.

What it does not tell you: overrides can come from the image rather than the command line, and they decide which algorithm NCCL picks

parallel

Measured in: counts

The parallel layout the process actually runs: TP, PP, DP, world size, the roles assigned to ranks, and whether TP exceeds the GPUs present.

What it does not tell you: TP in this block is what ran; arg.tensor_parallel_size is what was asked and can differ when the engine re-plans

pd

Measured in: a label

Prefill/decode disaggregation warmup, as a startup step.

What it does not tell you: its cost lands in startup, before the first request, and no flag accounts for it

plugins

Measured in: name pairs

Plugin registrations the server made: which name replaced which (`plugins.loaded: a -> b`).

What it does not tell you: the arrow direction is `registered name -> implementation`, and a missing arrow is a plugin that never loaded

quant

Measured in: format and kernel names

Quantization as the build reports it: checkpoint format, the kernel selected, and the per-layer choice when the log lists it.

What it does not tell you: a quantized checkpoint that loads is not proof the fast kernel was used; quant.kernel.selected is

ray

Measured in: prefixes

Ray's environment handling: which variable prefixes the workers inherit.

What it does not tell you: a variable missing from this list is missing in the workers, even if the engine process has it

sampling

Measured in: backend names, settings

Sampling kernel and overrides: which top-k/top-p implementation ran, whether it fell back, and which request settings were overridden by spec decoding.

What it does not tell you: a silent fallback to the torch kernel is slower, not wrong -- it shows here and nowhere in the flags

sched

Measured in: counts

Scheduler limits that were changed from what was configured: max scheduled tokens from spec settings, max running requests capped by a state cache.

What it does not tell you: sched.max_running_requests carries the cache that caused the cap in its value, because the number alone reads like a configured limit

scheduler

Measured in: labels

The scheduler's decisions: async scheduling on or off (and the reason), chunked prefill, and how it exited.

What it does not tell you: async scheduling can be accepted from the flag and then disabled by the executor; scheduler.async_reason is why

server

Measured in: URL, command, labels

The HTTP surface: the URL it binds, the command line it was started with, the tasks it advertises, and whether scale-out is enabled.

What it does not tell you: the number after `API server` in vLLM's line is a local rank in the DP group, not a port; the port is only in the URL

serving

Measured in: a label

How the served endpoint formats content (chat template content format).

What it does not tell you: it changes what the model receives for multimodal inputs, and no sampling flag records it

spec

Measured in: tokens, a label

Speculative decoding specifics: draft length, MTP layer reuse and whether the draft shares embedding/lm_head weights with the target.

What it does not tell you: sharing weights changes memory and numerics; a spec diff that only compares acceptance rates is missing it

startup

Measured in: a label, exception text

How startup ended: ready, or failed and at which stage. startup.error is the exception text the server printed; startup.cause is a timeout raised around it.

What it does not tell you: `stable` and `ready` are different claims: a failed run can still have printed every fact above it, so read this key first when the diff looks surprising

startup.error

Measured in: exception text

The exception as the server printed it, first line only.

What it does not tell you: a wrapper exception (worker init failed, ray task error) names the stage, not the cause; the cause is further down the same log

torch

Measured in: MiB, GiB

The CUDA allocator's own OOM report: which device, how much was requested, how much was free at that instant, the card's total, and torch.oom_holder_gib -- the GiB another process was holding.

What it does not tell you: oom_holder_gib is the answer to 'VRAM is enough, why did it die': on the A100 in vllm#54559 another process held 94.41 of 95.00 GiB

transfer

Measured in: count, MiB, backend name

KV transfer between prefill and decode workers: staging buffers, their size and method, the custom memory pool, and the NIXL backend.

What it does not tell you: staging memory is reserved per worker; a transfer diff that ignores it compares throughput of two runs with different memory available for the cache

triton

Measured in: versions

Triton driver/library versions as the log prints them.

What it does not tell you: a mismatch here often shows up first as a compile failure, not as a wrong number

uva_buffers

Measured in: a label

Whether Unified Virtual Addressing buffers could use pinned memory, and what the server fell back to.

What it does not tell you: pinned memory affects host-to-device speed and can change startup timing while changing no flag

weights

Measured in: GiB, seconds, MiB/s

Where the weights came from and how they were read: format, filesystem, cache, download and load seconds, checkpoint size, dtype, available RAM, and whether prefetch was possible (weights.prefetch says why not).

What it does not tell you: download_s is the network leg only; a slow startup on a local disk shows in load_s and in `weights.prefetch: disabled (...)`, not in download_s
