vLLM: "No available shared memory broadcast block found in 60 seconds" — what the line means, and how to tell which failure you have

This string shows up in dozens of threads, and the two answers that dominate search results are "increase /dev/shm" and "it is still compiling". Both are sometimes right. Both are wrong often enough that people keep re-posting the same log.

Here is the same question from the other end: instead of guessing the cause, read what the runs actually resolved and let the log separate one waiting line from sixteen stalls. Every command output below was produced by servediff 0.4.61 — except the repeats demo near the top, which is labelled as synthetic.

Three readings of this line, and how to tell them apart

The line is emitted from the writer side of shm_broadcast.py, once every VLLM_RINGBUFFER_WARNING_INTERVAL (60 s) while it waits. That much is fixed. What people disagree about is why the writer is waiting, and the published answers fall into three groups:

reading who publishes it what it predicts in the log
/dev/shm is too small most guides, e.g. kubesimplify ("you probably forgot --ipc=host") a different error, raised at buffer creation, before any 60 s wait exists
workers are still compiling / capturing graphs same guide ("shows up while vLLM is busy compiling or capturing CUDA graphs") the lines stop once Graph capturing finished appears
one reader stopped draining, writer pinched LMCache's MI300X notes ("Both TP workers alive, no preemptions"), GB10 UVM livelock notes the wait outlives capture, and the cadence stays a metronome

Three cheap checks decide between them, and all three are arithmetic on the log:

Check 1 — does /dev/shm capacity explain it? It cannot, if the capacity check passed. That check runs at buffer creation and fails loudly, with the fix already in its message:

RuntimeError: Insufficient space in /dev/shm: N MiB required, M MiB free.
Increase /dev/shm (e.g. --shm-size or --ipc=host).

You cannot reach the 60-second watchdog with a full /dev/shm; you get this instead. So a run that logs the 60 s line had enough shm at creation. (--ipc=host remains the right answer to a different error.)

Check 2 — did the wait outlive graph capture? Count the lines after Graph capturing finished. In the log analysed below, Graph capturing finished is at 11:37:55 and 14 of the 16 lines come after it, through 11:50:31. "Still compiling" cannot explain a tail that starts 13 minutes after compiling ended.

Check 3 — is the cadence a metronome? If the gaps hold at exactly one interval, it is one continuous wait re-logging itself, not sixteen independent stalls. Sixteen real stalls are irregular; this is not.

Two of the three checks are pure counting, which is why servediff ships them as a subcommand:

$ servediff repeats repro.log --top 3
/tmp/repro.log: 56 line(s), 2 shape(s) repeated 2+ time(s), 55 line(s) in them
    39x burst    11:33:26 -> 11:33:26.380  span 0.38 s
        gaps 0.010 s median, 0.010 s max
        [rank0]:[W113 11:33:26.000 CUDACachingAllocator.cpp:3933] memory allocation failed with OOM on device 0 while trying to allocate 20971520 bytes
    16x regular  11:34:32 -> 11:49:32  span 900 s
        gap 60.000 s median, 60.000 s max
        [W113 11:34:32 shm_broadcast.py:801] No available shared memory broadcast block found in 60 seconds.

  A regular gap is one wait being re-logged, not N separate failures: compare that span with
  anything that could have blocked a reader.

(This demo runs on a 56-line synthetic log carrying the two shapes; on the real log below the same two shapes read 2.318 s and 959 s.)

The rest: what to compare between two runs

The question behind most of these posts is "what changed", and a benchmark number cannot answer it. The startup log records what the server resolved on the way there — which attention and all-reduce backends it picked, whether CUDA graphs were captured, which fusions ran, what the KV-cache pool ended up being, and whether it finished with ready or a traceback. Two logs from two runs therefore contain the answer, in plain text, without a profiler.

pip install servediff
servediff diff a.log b.log

One flag: did it take effect?

Same vLLM version, same NVFP4 checkpoint, second launch taking the Marlin kernel path instead of CUTLASS. The diff is two rows:

$ servediff diff vllm-47047-v0.23-default.log vllm-47047-v0.23-marlin.log   # excerpt
fact                             baseline               candidate               status
backend.moe                      VLLM_CUTLASS (NvFp4)   MARLIN (NvFp4)        changed
kv_cache.max_concurrency         <absent>               54.14                 only_candidate

2 difference(s); 0 fact(s) identical. Absent means the log did not print it, not that it was off.

Both of these logs are single-rank, so the live command prints two note: lines before the table (it cannot tell whether an absent all-reduce path means "single rank" or "not used"); the fact rows above are verbatim. The 2 difference(s) counter and exit code 1 are what the run returns.

That is what "the flag did take effect" looks like. The expensive case is the mirror image: same command line, backend.moe identical in both logs. A flag that silently did nothing produces a diff of zero server-side facts, and no amount of benchmarking will distinguish "the flag is neutral" from "the flag never reached the engine". The log diff distinguishes them in one line.

Version bump, same flags

v0.23 → v0.26 on the same configuration. Nothing on the command line changed:

$ servediff diff vllm-53472-v0.23.log vllm-53472-v0.26.log   # excerpt
fact                             baseline                              candidate                              status
backend.candidates               ['FlashInfer TRTLLM', 'FlashInfer CUT... <absent>                               only_baseline
backend.moe                      FlashInfer CUTLASS (Unquantized)        TrtLlmBf16ExpertsMonolithic            changed
backend.moe_prepare_finalize     <absent>                                MoEPrepareAndFinalizeNoDPEPMonolithic  only_candidate

3 difference(s); 0 fact(s) identical.

The MoE backend moved from a CUTLASS path to a TRT-LLM monolithic expert kernel, and a prepare/finalize path appeared that the older release never printed. Those are the facts a throughput comparison is actually comparing.

absent is a claim with a meaning

The distinction that matters most in practice:

  • <absent> means this run never printed the line. It is not the same as "off", and not the same as "false".
  • --skip-absent then reports only facts both sides printed, and counts what it left out:
$ servediff diff a028.log a030.log --skip-absent
3 difference(s); 14 fact(s) identical. 50 difference(s) skipped because one side never printed those lines (--skip-absent). Absent means the log did not print it, not that it was off.

The unfiltered run of the same pair reports:

53 difference(s); 14 fact(s) identical. Absent means the log did not print it, not that it was off.

Fifty of those 53 are one-sided, so a naive diff of 53 rows would overstate the change by a factor of about 18. The 3 that survive are the ones both engines actually resolved, and only those can be compared as values. The full 53-row table for this pair, with the command, exit code and the reason the baseline died early, is kept in the repository so it has a permanent home: writeups/wsl-uva-028-vs-030.md.

One log can contain two different failures

From vLLM #54559 — 102 lines, TP2, single GPU, 79.14 GiB:

$ servediff show 54559.log        # excerpt
gpu.total_gib           79.14          line 87
gpu.free_gib            78.46          line 87
gpu.consumed_gib        [64.46, 64.39] line 87
gpu.budget_gib          75.18          line 87
model_loading.gib       63.31          line 40
cuda_graph.capture_gib  3.26           line 87
cuda_graph.capture_s    85             line 86
torch.oom_requested_mib [20.0, 14.0]   line 1
torch.oom_free_mib      [9.19, 10.75]  line 1

Two things fall out of those numbers, neither of which the issue text says:

39 OOM lines are two allocator bursts, not 39 failures. They run from 11:33:26.640 to 11:33:28.958 — 2.318 s — alternating [rank0]/[rank1], 7–16 ms apart with one ~1 s gap, the request dropping from 20 MiB to 14 MiB. And the card was not full: gpu.free_gib 78.46 while the allocator saw 9.19 MiB free, because the pool is set to 0.95 × 79.14 = 75.18 GiB. The failure is inside the allocator's own budget, not on the device.

16 broadcast-wait lines are one 959 s wait, not sixteen stalls. All from EngineCore pid=260, 11:34:32 → 11:50:31, one line per 60 s interval, a single +118 s step, and 14 of the 16 arrive after Graph capturing finished at 11:37:55. Checks 2 and 3 from the top of the post are answered by that sentence alone: the wait outlived capture, and the cadence held.

The diff bounds the problem; it does not name the cause

From vLLM #63705 — MiniMax-M2.7, TP4+EP, 4×H100. The reporter's own table puts the regression entirely in decode: ttft −0.9 / −1.8 / −0.8 % on 0.29.0 / 0.31.0 / 0.32.0, tpot +22.7 / +27.9 / +22.1 %, throughput −17.9 / −21.1 / −17.5 %. A benchmark table like that cannot say which server-side component moved. The startup logs can:

fact v0.26.0 v0.29.0
TP group all-reduce chain ['PYNCCL'] ['FLASHINFER', 'PYNCCL']
EP group all-reduce chain ['PYNCCL'] ['PYNCCL']
model runner V1 (line absent) V2 (Using V2 Model Runner)

FlashInfer all-reduce entered the TP dispatch chain and EP stayed on PYNCCL, so the candidate change is TP-side; Model Runner V2 became active on this configuration. Two named variables to A/B, from lines that were already being written to disk.

And the honest part: an external contributor later re-ran that benchmark on 4×H100 with the same serve flags and did not reproduce the regression — v0.29 came out about 8 % faster. So the diff did not solve the issue; it told both sides what to test. A log says what is configured, not what it costs. Reading the dispatch list as "every collective used FlashInfer" is specifically wrong: it is a candidate set tried in order, falling through when a backend rejects the input.

What servediff is, and what it refuses to do

It reads startup logs from vLLM and SGLang and answers "what did each server actually run with":

pip install servediff
servediff diff a.log b.log              # facts, side by side, each with its source line
servediff diff a.log b.log --markdown   # same as a table
servediff show a.log                    # one log's facts with line numbers
servediff repeats a.log                 # one re-logged wait vs N real failures
servediff capture -o run.log -- <command>   # run a server and keep its startup log
servediff demo                          # two bundled logs, if you have none of your own yet

It does not profile, does not judge which change caused the slowdown, and does not guess when a line is missing. Its job is to make the 53-row diff collapse into the 3 rows that can actually be compared, and to keep absent from being read as off.
